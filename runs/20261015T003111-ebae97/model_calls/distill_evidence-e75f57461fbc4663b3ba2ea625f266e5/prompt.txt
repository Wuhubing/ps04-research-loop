The failure mode these designs are most explicitly built around is an inability to reliably search the space of ML solutions, so we focus our trace analysis on search, studying in depth the traces of Kimi K3 and GLM 5.2 under MLEvolve, AiScientist, Malena and Oneshot iterations.\nPrior designs typically impose an explicit search structure — a tree over candidate ideas (Arbor, MLEvolve), a population of competing programs, or a stagnation-triggered switch to a fresh idea (ScienceFlow) — built around a discrete unit of work or checkpoint that is either refined or abandoned. Malena’s workflow with GLM 5.2 and Kimi K3 differs qualitatively: it produces a single general pipeline spanning a task’s natural stages (e.g., the two-stage embed-then-retrieve pipeline on whale; see Appendix [E.5](#A5.SS5)), then spends the rest of the run on what amounts to hyperparameter search, but over code patches rather than parameter values. This lets it reuse checkpoints and utility code (data loading, preprocessing, validation splits) across iterations, improving efficiency and narrowing the generalization gap.\nGoing further, we annotate each trajectory’s checkpoints with the ML techniques used (see Appendix [E](#A5) for the full labeling methodology) to see how each method searches and what it searches over. Two findings stand out.\nFirst, methods with LLM-driven search (Malena and AiScientist) start out balanced across the stages of a standard ML pipeline — data preprocessing, feature engineering, architecture, training, and beyond — with AiScientist slightly skewed towards model selection early on. Both become more performance-oriented towards the end of the run, concentrating on ensembling and, at times, techniques borrowed from the Kaggle community such as pseudo-labeling (Appendix [E.5](#A5.SS5) gives a worked example of Malena independently rediscovering this technique under two different backbones). This late-run shift is more pronounced for Malena than for AiScientist, with the shares of ensembling, model selection, and post-processing all increasing until the very end of the run. MLEvolve, in contrast, settles into a roughly stable technique distribution after about the first 10% of the run (Figure [5](#S5.F5)).\nSecond, this skew towards performance does not confine Malena to well-known recipes: Figure [4](#S5.F4) shows that Malena and MLEvolve are consistently the top two methods in technique rarity (see Appendix [E.2](#A5.SS2) for how rarity is computed), i.e., the techniques they use tend to appear in fewer of the other groups’ runs. Malena therefore keeps proposing comparatively rare techniques while becoming more performance-oriented late in the run.\nTogether, these results suggest that a sufficiently capable coding-agent backbone can drive this kind of search largely on its own: Malena balances exploring genuinely rare techniques against a growing performance focus as the run progresses, all while efficiently reusing the checkpoints, utility code, and other artifacts it has already produced rather than starting over, with no hand-built harness needed to elicit this behaviour.\n6 Conclusion\nSystems for autonomous machine learning engineering have grown steadily more elaborate: search trees over candidate solutions, populations of competing programs, teams of specialized agents. That machinery was designed when the underlying unit of work was a single model completion, which cannot run the code it writes, remember what it already tried, or react to an error. Coding-focused post-training has since changed the primitive itself: a model highly capable of autonomous work plans, executes and debugs inside one long-running session, without an outer program telling it what to do next. This paper asks which of the accumulated machinery still earns its keep once the primitive can do these things itself, and answers it by ablating that machinery layer by layer at a fixed model, budget and task set.\nAlmost all of the gain comes from the runtime and LLM backbone, and almost none from what is built on top of them. Giving the model a shell and a filesystem instead of a chat interface is the single largest effect we measure. Once that is in place, and as the coding agent is given more autonomy, the techniques accumulated by the test-time-compute literature over the last few years barely move the result. A model highly capable of autonomous work already does much of what these techniques were designed to supply from outside, so supplying it again buys little. A single long-running agent session with minimal machinery on top turns out to be a strong baseline, and none of the standard components we added improved on it.\nWe then confirm the same picture from the outside, against state-of-the-art systems built specifically for this task. Holding the model, hardware, and budget fixed, none of the published harnesses we tested significantly outperforms the plain agent session with frontier backbones. With GLM 5.2, Malena earns a medal on 62.5% of the competitions, compared with 47.1% for the best external harness tested. Across all backbones, our statistical analysis either favours Malena over the other harnesses or finds no significant medal-rate difference between them.\nThe practical reading is that effort spent elaborating harnesses around a model that is already strong at working autonomously has poor returns. The leverage is in the model and in the runtime it is given, not in the scaffolding built around them.\nLimitations\nMost of our results rely on MLE-bench, which has known task-preparation\nissues and, being built from public Kaggle competitions, is a plausible contamination target;\nwe mitigate this by fixing broken tasks, directly checking for contamination, and additionally\nevaluating on NatureBench. A second limitation is statistical power: some results still have\nconfidence intervals wide enough to preclude strong claims about effect size, though we believe\nthe weaker no-worse-than claims are well supported.\nA third is scope: most harness interventions we test operate within a single worker, and we leave a more in-depth exploration of sophisticated inter-agent coordination protocols to future work.\nA fourth is possible asymmetry in tuning effort between Malena and the external harnesses it is compared against; Appendix [D.3](#A4.SS3) documents the backbone-specific bug fixes and configuration ablations we applied to each external harness to mitigate this.\nFull discussion in Appendix [G](#A7).\nReproducibility statement\nFull experimental settings are described in Section [3](#S3) and in\nAppendix [B](#A2): the coding agent framework and tool set exposed to the\nmodel in each iteration (Appendix [B.2](#A2.SS2)), the search strategies compared\n(Appendix [B.3](#A2.SS3)), and the exact LLM backbones and hosting configuration\nused, with their HuggingFace identifiers (Appendix [A.4](#A1.SS4)). For an experiment with \\(T\\) different tasks, each task \\(t\\) containing \\(N_{t}\\) seeds, for metric \\(\\mathrm{metric}\\), we report:\n|  | \\[\\frac{1}{T}\\sum_{t=1}^{T}\\frac{1}{N_{t}}\\sum_{r=1}^{N_{t}}\\mathrm{metric}(\\mathrm{run}_{t,r}).\\] |  | \nOur confidence intervals are estimated via bootstrap on the fixed set of \\(T\\) tasks, sampling for each task from the \\(N_{t}\\) available seeds before computing the macro average, and taking the quantiles of the simulated distribution. For each plot and table presented, the comparison is always based on the same task set. In the tables presented in this paper, we mark as bold numbers the best results obtained across arms, and when present, with underlined and italics the second and third best, respectively.\nFor our \\(A\\) vs \\(B\\) comparisons, we compute the paired-by-task difference to isolate positive or negative effects on the ablation:\n|  | \\[\\frac{1}{T}\\sum_{t=1}^{T}\\left(\\frac{1}{N(A)_{t}}\\sum_{r=1}^{N(A)_{t}}\\mathrm{metric}(\\mathrm{run}(A)_{t,r})-\\frac{1}{N(B)_{t}}\\sum_{r=1}^{N(B)_{t}}\\mathrm{metric}(\\mathrm{run}(B)_{t,r})\\right).\\] |  | \nTo determine statistical significance, we compute the 95% CIs of the paired-by-task difference (again, on the fixed set of \\(T\\) tasks, bootstrapping from \\(N(A)_{t}\\) and \\(N(B)_{t}\\)). If \\(0\\) does not lie in the CI — which we mark with * in our paired-by-task tables throughout the paper — we can establish a statistically significant difference in the metric in the ablation. When \\(0\\) lies in the CI, the arms become statistically indistinguishable at our power level based on the amount of seeds we ran in our experiments. With this method, between-task difficulty cancels, which results in narrower intervals than regular marginal CIs.\nAppendix B Implementation details\nIn this section, we provide more details about our core iterations ablated, along with their optional tool and infrastructure addons below.\nB.1 Iterations\nAll three iterations are compiled from a single prompt-template family. All iterations share a base prompt with the agent persona, the scientific-approach questions, the resource and time budget line and a few general recommendations. A specialized task description and instruction block is then chosen for each iteration and aligns with the goal and environment available for each method.\nIn the task description, the Oneshot and Malena iterations are handed only the data paths (raw data directory, description file and sample submission file) since they can explore the data themselves through their tools.\nOn the other hand, Chat receives the task description verbatim and an inline overview of the data computed by the harness: a directory tree of the data folder, per-file previews (per-column statistics for CSVs — dtype, cardinality/value counts, mean, range and NaN counts — auto-generated schemas for JSON files, and the first lines of text files, subject to a global character budget), and the first rows of the sample submission.\nAll iterations execute inside a git worktree checked out at their parent node’s commit, and each produces a node whose recorded validation score tuple is what the search rules of Section [4.2](#S4.SS2) (Appendix [B.3](#A2.SS3)) consume.\n- 1. \nChat. A single chat-completion call with no tool access. The model receives the base prompt with the inline data overview and is instructed to reply with a complete, self-contained Python script that implements the full pipeline (data \\(\\to\\) model \\(\\to\\) training \\(\\to\\) inference) and writes submission.csv. The response text is saved verbatim to main.py after stripping any enclosing code fences, and executed once with the remaining time budget. If the run succeeds and the submission validates against the expected format, the agent is queried again with the output of the command to extract the validation score, and the iteration ends. Otherwise the harness re-prompts the model — appending to the same conversation — with a failure report containing the failure reason (non-zero exit, missing or invalid submission), the truncated stdout/stderr, a hardware-utilization summary, and a footer that disambiguates system kills (GPU-memory watchdog, RAM watchdog) from ordinary crashes. The model must answer with the full corrected script. This loop repeats until a valid submission is produced.\n- 2. \nOneshot. One coding-agent session, one conversation turn, under the default tool environment of Appendix [B.2](#A2.SS2).\nThe prompt instructs the agent to treat the worktree as a scratch directory to confirm its design with cheap verification runs (fast data-inspection scripts, then minimal test runs), and to converge to exactly one production run.\nAfter one production run succeeds, no further heavy training is permitted, and failures may only be diagnosed with cheap runs, never with a second production attempt.\nFour deliverables are required: main.py (the pipeline), submission.csv, design.md (a self-contained write-up of the design, results and rationale, meant to serve as the node’s documentation for later iterations), and score.txt (a single floating-point validation score on the task’s metric and direction). These deliverables are expressed as guarantees: when the agent ends its turn, the harness statically verifies the file set and re-prompts the agent with the list of missing or malformed guarantees (e.g. an unparsable score file) until all hold. When the parent node already carries a scripted solution (a previous main.py and design.md), the prompt switches to an improve variant: the agent is instructed to study the documented design, to decide between refining and pivoting using the recorded execution cost and results, and to overwrite the same files (any other scripts are discarded).\nThis is the mechanism by which the search strategies of Section [4.2](#S4.SS2) share information between nodes.\nThe implementation also supports appending optional instructions to the prompt as described in Appendix [B.2](#A2.SS2).\nThis addition is only added when the corresponding intervention is enabled.\n- 3. \nMalena. The same coding-agent environment as Oneshot, but the session is allowed to span the iteration’s entire time budget in place of a single production run, and the one-production-run and documentation requirements are lifted. The instructions grant the agent freedom to design any number of pipelines and produce any number of submissions, dividing its budget as it sees fit. The harness drives the session as a turn loop: whenever the agent ends a turn before the budget expires, it is re-prompted with a short follow-up message that reports the remaining time. Submissions are generally tracked using the submission plugin. The agent calls submissions_register itself (optionally consulting submissions_list), reporting each submission together with its validation score and free-form metadata, with the prompt making explicit that only registered submissions count and that each registration is atomic and immediate. When the submission plugin is disabled, the agent simply saves submission files under a submissions/ directory and the harness salvages and registers every file found there at wrap-up (without a validation score). Unless explicitly stated, all experiments reported use the submission plugin with validation score signals.\nB.2 Infrastructure\nThe discussion in this section only applies to coding agent iterations (Oneshot and Malena).\nOur core coding agent loop harnesses over OpenCode. It preserves all default tools, except we explicitly disabled doom_loop, plan_exit, and question. Moreover, we overwrite the native bash tool with our own implementation (more information in the following overview). The most important and used tools for the coding agent are:\n- • \nread: Reads the contents of a file.\n- • \nwrite: Writes the contents of a file.\n- • \nedit: Edits the contents of a file.\n- • \nbash: Executes a command. The tool blocks until all subagents finish their work.\n- • \ntodowrite: Allows the agent to maintain a task list of goals during its session.\nOn top of this, we additionally ablated the following tools. The default Malena configuration has submission, system, and jobs tools enabled. The other coding agent iterations run with them disabled, unless otherwise specified for any particular ablation.\n- • \nsubmission_register tool: Adds a submission file to the registry. We equip the agent with eight skills encoding common ML engineering strategies for iterating on a competition: submission-blueprint (build and verify the end-to-end submission pipeline first, using a trivial predictor, before training a real model); quick-strong-baseline (get the highest score for the least training and implementation effort, leaning on pretrained models and off-the-shelf libraries); cost-saving-techniques (a toolbox of levers — frozen backbones, low resolution, few epochs, data subsampling — for getting a faithful signal cheaply, meant to be folded into the other skills); simplification-probe (shrink the task, either by holding one axis at full difficulty while collapsing the rest, or by reformulating it as a smaller proxy task, to isolate where a score gap comes from); ablation-probe (design a controlled comparison that isolates one component’s contribution, holding everything else fixed); runtime-estimate (measure a few scaled-down configurations and extrapolate wall-clock and memory cost before committing to a full-scale run); stagnation-pivot (detect when recent attempts within the same paradigm have stopped improving and force the next attempt to pivot the model, loss, input representation, or problem decomposition rather than tweak a hyperparameter); and cross-iteration-synthesis (step back and read across several past attempts together to compose ideas, extract best practices, standardize the validation protocol, or resolve contradictions).\n- H \nhuggingface_hub_repo_search: The official HuggingFace MCP. [Chen et al., 2026b](#bib.bib7)), which recursively selects among the children of the current node, we score every node in the tree and take a single global supremum.\nIn the following, assume the competition metric is higher-is-better (the lower-is-better case is analogous, replacing each normalized score by its complement).\nLet \\(T\\) be the current tree, \\(V(T)\\) its nodes, and \\(\\mathrm{s}(n)\\) the validation score recorded on node \\(n\\).\nThen, \\(\\hat{s}(n)=\\max_{n^{\\prime}\\in\\mathrm{subtree}(n)}\\mathrm{s}(n^{\\prime})\\), so that a node’s value reflects what its descendants eventually achieved.\nThis maximum backup replaces the running mean fitness used in canonical UCT implementations ([Toledo et al., 2025](#bib.bib41); [Du et al., 2026](#bib.bib11)), which is appropriate here because candidates are deterministic artifacts to be kept rather than stochastic returns to be averaged.\nUCB1 then computes\n|  | \\[R(n)=\\frac{\\sigma(\\hat{s}(n))}{\\|V(T)\\|-1}+c\\sqrt{\\frac{\\ln\\left(\\|V(T)\\|+1\\right)}{\\|C(n)\\|+1}},\\] |  | \nwhere \\(\\sigma(x)\\) is the \\(0\\)-indexed rank of \\(x\\) among all available scores, \\(C(n)\\) are the children of \\(n\\), and \\(c>0\\) is the exploration-exploitation hyperparameter (fixed at \\(c=0.75\\) for all runs).\nRanking rather than using the raw metric is what makes a single \\(c\\) transferable across competitions: MLE-bench metrics are arbitrarily scaled and of mixed direction, and a rank transform is invariant to any order-preserving reparameterization of the metric while remaining robust to outlying runs, in the manner of the rank-based fitness shaping used by evolution strategies ([Hansen & Ostermeier, 2001](#bib.bib17); [Wierstra et al., 2014](#bib.bib44)).\nPrior MLE harnesses instead min-max normalize the metric ([Chen et al., 2026b](#bib.bib7)), substitute a bounded hand-designed reward ([Du et al., 2026](#bib.bib11)), or leave the metric raw and retune the exploration constant per setting ([Toledo et al., 2025](#bib.bib41)).\nKeeping the first term in \\([0,1]\\) also lets us adopt the exploration constant that the UCT analysis prescribes for bounded rewards, \\(c\\approx 1/\\sqrt{2}\\), without per-task tuning ([Kocsis & Szepesvári, 2006](#bib.bib22)).\nOur strategy for Best-of-N methods consists of running independent single Oneshot iterations, and then composing a set of bootstrapped-trajectories \\(B_{j}=\\{T_{1}^{j},\\ldots,T_{N}^{j}\\}\\) where each \\(T_{i}^{j}\\) is a composition of multiple independent Oneshot iterations of the requested time limit budget. Each trajectory is packed greedily so that the summed effective time of its iterations does not exceed the target budget, and an iteration that would overflow the trajectory is discarded rather than carried into the next one. The budget is therefore matched on the time the iterations actually consume, not on their nominal per-iteration time limit. We can then extract all metrics for each trajectory \\(T_{i}^{j}\\) by concatenating the submissions of all iterations in the trajectory. Finally, we sample multiple independent bootstrapped-trajectory sets \\(B_{1},\\ldots,B_{M}\\) and report the average-of-averages across this set.\nAppendix C Additional Chat, Oneshot and Malena ([Du et al., 2026](#bib.bib11)) MLEvolve maintains a tree of candidate solutions, each node a\ncomplete training script with a single parent, and expands it by UCT: nodes carry visit\ncounts and a backpropagated reward, and selection descends by the usual\nupper-confidence-bound rule with an exploration constant that decays over the run. The\nbackpropagated reward is not the task metric but a small hand-designed signal — a bonus\nfor beating the incumbent, a penalty for a node that fails to run. Past the halfway point\nof the budget the selector blends UCT with rank-weighted sampling from a global,\ngreedily-ranked top-\\(K\\), so exploration gives way to exploitation on a schedule rather than\nthrough the search rule itself. Six operators produce nodes: draft,\nimprove, evolution (improve using the branch’s own trajectory),\ndebug, and two cross-branch operators, fusion and fusion_draft,\nwhich synthesize a candidate from the best nodes of several branches. Crossover therefore\nflows through the prompt rather than the topology: a fusion node still has exactly\none parent, with the other candidates injected as reference text, so the structure is a tree\nwith cross-branch information flow and not a genealogical graph. Three candidates execute\nconcurrently on one GPU. It commits, greedily and with no end-of-run re-ranking, whichever\nsubmission had the best self-reported validation metric at the time it was produced — a\nnumber an LLM extracts from the candidate’s own stdout. It also keeps a hybrid BM25+FAISS\nretrieval memory over past attempts within a run, indexing each successful node by its plan\nand a code summary (and each debug node by the error it was repairing) and querying it when\ndrafting, improving and debugging; we enable it in all runs reported here.\nAiScientist. ([Chen et al., 2026a](#bib.bib6)) AiScientist has no search structure: it is a single conversation\nstepping through tool calls, and what to do next is whatever tool the model names. State\npersists in one mutable git repository plus two append-only markdown logs, one for\nimplementation and one for experiments; whenever the agent implements or runs an experiment,\nthe harness greps the most recent block of the other log and prepends it. This\n“file-as-bus” is the whole of its memory — there is no retrieval index, and the only\nother summarization fires on context overflow. Its operators are analyze_data,\nprioritize_tasks, implement (whose modes cover full/fix/explore/refine/ensemble, so debugging is a mode rather than a separate operator), run_experiment,\nspawn_subagent and submit, alongside shell primitives. Work is strictly\nsequential; subagents run blocking, and the only concurrency is whatever background training\nthe model chooses to launch inside its sandbox. Most consequentially for\nSection [5.1](#S5.SS1), the final choice among candidates is made by the agent rather\nthan by harness code: no code ranks candidates, but the agent is required, as a step before\nsubmitting, to compare its candidates against the registry and its experiment log and copy\nthe best to the canonical submission path. It does so substantively — where it records the\ndecision, it cites the cross-validation or hold-out protocol it designed, per-candidate\nscores under that protocol, and a rationale comparing them (for instance choosing a blended\nensemble at OOF \\(F_{1}\\) \\(0.944\\) over its two components at \\(0.942\\) and \\(0.938\\)). Its\nself-selected number is therefore a genuine self-selection on its own validation signal, as\nfor the other methods; the difference is that the mechanism is prompt-driven rather than\nenforced, and the structured record of it is present in only a minority of runs.\nArbor. ([Jin et al., 2026](#bib.bib20)) A research agent built around a Coordinator/Executor loop over a\npersistent “Idea Tree”: the Coordinator maintains the tree of candidate ideas and their\noutcomes, the Executor implements and evaluates a chosen idea in an isolated git worktree\nper experiment, and the loop expands whichever branch of the tree looks most promising.\nTwo run modes exist upstream: a native CLI over a swappable backbone LLM, and a\nkeyless coding-agent skill-suite mode where the host coding agent’s own model does the\nreasoning; this paper uses the native-CLI mode.\nScienceFlow. ([Zhao et al., 2026](#bib.bib52)) A config/manifest-driven long-horizon ML-research agent\n(scienceflow.cli, verbs repl/parallel/monitor): a run\nis specified as a YAML task manifest and executed by one or more parallel exploratory\nworkers under a chosen concurrency level, orchestrating both the agent’s own reasoning\ncalls and the ML training/evaluation code the workers produce.\nD.2 Detailed Labeling was run on a fixed set of\n10 original MLE-bench tasks (aptos2019, billion-word-imputation,\ncassava, champs, freesound, h&m, jigsaw,\nnfl, petfinder, ventilator) – not to be confused with the\nfixed10 challenging split used elsewhere in this paper, which is a different\nset of 10 tasks. The checkpoint-mining and\nlabeling steps below (through canonicalization) are the current pipeline behind\nFigure [5](#S5.F5) and\nFigure [4](#S5.F4). Unless stated otherwise, the\nlabeling/judge model throughout is GLM 5.2.\nE.1 Checkpoint mining\nCheckpoints. We unify run traces across methods to a common checkpoint format: a snapshot of the run’s code repository at specific points in time, method-dependent since each harness structures its own trajectory differently – for Malena, immediately before a long job submission, a long bash tool call, or a submission-registration tool call; for MLEvolve, before executing a candidate; for AiScientist, before a long bash tool call; for Arbor, before a job-submit call. Oneshot and Completions have no intermediate trajectory to snapshot and are labeled once, on the final state of the repository. Runs with multiple checkpoints are labeled sequentially along this chain, each job seeded with the entries already logged for its nearest earlier checkpoint so it only has to add, remove, or revise entries rather than re-deriving the whole technique set from scratch.\nLabeling schema (pass 1: technique extraction). The judge (GLM 5.2) reads a checkpoint’s code and logs zero or more entries, each with: a free-form snake_case name (no reuse-search against prior entries – naming convergence is handled later, offline); 1–3 categories, ordered most-to-least applicable, drawn from a fixed 13-way taxonomy (data_preprocessing, data_pipeline, feature_engineering, augmentation, architecture, loss, regularization, optimization, training, ensembling, model_selection, post_processing, inference, plus an other escape hatch (used for only 0.02% of all logged category-tag annotations across our labeled checkpoints), which we exclude from the category-share figures throughout this section); and three separate text fields instead of one blob – mechanism (task-agnostic, roughly 40 tokens, describing only WHAT IS COMPUTED, stripped of domain nouns and hyperparameters, the only field ever embedded for similarity/dedup), instantiation (task-specific detail, hyperparameters, and domain nouns, kept for search but never embedded), and evidence_sig (a 1–3 line canonical code excerpt for human/reviewer sanity-checking). Splitting mechanism from instantiation this way removes a specific noise source found in an earlier embedding-similarity audit, where chunk embeddings picked up code-context co-occurrence (e.g. dropout/mlp/layer_norm clustering together purely because they appear near each other in a forward pass) rather than technique identity.\nDeduplication and canonicalization (offline, per task). All identity resolution – deciding whether two independently-logged entries describe the same underlying technique – happens offline, never at labeling time, and entirely within one task’s own runs (never pooled across tasks, so no task’s vocabulary is built from or reviewed against another task’s runs). Pass-1 entries are embedded on their mechanism text using Qwen3-Embedding-8B and grouped by complete-linkage hierarchical clustering at a fixed cosine-similarity threshold (0.70, picked by sweeping method \\(\\times\\) threshold against a hand-audited corpus for cluster-size and same-run-duplicate violations). An automated GLM 5.2 review then runs in two phases: a split-review phase flags multi-member clusters with no category shared by every member and asks GLM 5.2 whether any member should be extracted into its own cluster; a merge-review phase takes every singleton cluster and asks the judge whether it is really the same technique as one of its nearest neighbors by mechanism-embedding similarity. A final canonicalization pass has GLM 5.2 synthesize one canonical name and mechanism description per cluster that a reader would recognize as covering every member’s variant, rather than mechanically picking one member’s text. Pass 2 then re-labels every run a second time, this time against the finalized, canonical cluster set: the judge calls log_known_technique(cluster_id, ...) directly when a checkpoint’s technique matches an existing cluster, and free-form entries otherwise, so a pass-2 match is never subject to a separate, error-prone post-hoc nearest-centroid assignment step.\nE.2 Main-text plot methodology\nThis subsection gives the exact construction behind the two main-text plots built on top\nof the canonical technique clusters above: the category-share-decay curves\n(Figure [5](#S5.F5)) and the per-technique rarity distribution\n(Figure [4](#S5.F4)).\nCategory-share decay (half-life). Figure [5](#S5.F5)\ntracks a method’s technique-category composition as a function of checkpoint\nfraction \\(x\\in[0,1]\\) (progress through a run, pooled over every checkpoint of every run\nof that method). Every technique discovered at fraction \\(f\\leq x\\) contributes weight\n\\(0.5^{(x-f)/h}\\) to \\(x\\)’s composition, for half-life \\(h\\): a technique discovered exactly at\n\\(x\\) has full weight 1, one discovered \\(h\\) earlier has weight 0.5, and older ones decay\nsmoothly toward (but never reach) 0. Weighted category-tag counts are normalized to shares\nat each \\(x\\). \\(h\\to\\infty\\) recovers a plain cumulative count of every technique discovered\nso far; \\(h\\to 0\\) recovers an immediate, local snapshot of only the most recently discovered\ntechniques. The main text uses \\(h=0.25\\); Appendix [E.3](#A5.SS3)\nbelow checks smaller half-lives and per-task (non-pooled) curves.\nTechnique rarity.\nFigure [4](#S5.F4) reports, per method,\nthe distribution of how rare the canonical technique clusters that method’s runs exhibit\nare. Rarity is computed independently per task, not globally: for a fixed task, pool\nevery run of every (method, backbone) group on that task, and for each cluster \\(c\\) let \\(n_{c}\\)\nbe how many of those pooled runs exhibit it; \\(c\\)’s rarity is \\(1-n_{c}/n_{\\text{total}}\\), the\nfraction of that task’s pooled runs that did not use it. Pooling within the task\nacross every group (rather than, say, comparing a group only to one fixed baseline) means\nrarity reflects how many runs overall exhibit a technique, not how many distinct\ngroups do – a technique used by only a handful of runs stays rare even when those runs\nhappen to span more than one group (Appendix [E.5](#A5.SS5) gives a\nrarity-0.9 example shared across exactly two groups).\nFigure [4](#S5.F4) plots, per method, the resulting distribution of\nthese per-technique rarity values (pooled across backbones and 10 tasks) into\nsix windows centered at rarity \\(0,0.2,\\ldots,1.0\\) (half-width \\(0.1\\)).\nE.3 Robustness of the category-share-decay curves\nFigure [5](#S5.F5) in the main text pools all\nlabeled tasks at a single half-life (0.25). We mitigate this in three ways. First, we identified\nand fixed the subset of fixed30 tasks with broken preparation scripts (missing data\nor ground-truth leakage) rather than excluding them, so that our comparisons stay on the\nfull 30-task set used elsewhere in the paper; see Appendix [A.1](#A1.SS1) and\nTable [3](#A1.T3) for which tasks were fixed. Second, we directly checked for contamination via\ntwo independent methods, a code-similarity (Dolos) check and a bag-of-embeddings\nsimilarity check, both against a curated corpus of real fixed30 solutions and both finding\nno anomalous similarity between Malena-generated code and real solutions (Appendix [F](#A6)).\nThird, we additionally evaluate on NatureBench ([Wang et al., 2026b](#bib.bib43))\n(Appendix [A.3](#A1.SS3)), whose tasks are recent open scientific-research questions\nwith no public solution corpus to memorize, though there we could only afford a smaller\nnumber of models and fewer methods than on fixed30.\nA second limitation is statistical power. Some of our results still have confidence\nintervals wide enough that we cannot make strong claims about the size of an effect; we\nbelieve our weaker claims of Malena being no worse than a given baseline are well\nsupported (Appendix [A.5](#A1.SS5) reports the paired-comparison methodology this\nrelies on), but stronger claims about exactly how much better should be read with this in\nmind. This is a direct consequence of cost: running agents for the full 24-hour budget is\nexpensive, so we could only afford 3–4 seeds per task at 24 hours, versus 6–10 seeds per\ntask for our 6-hour and completion-only conditions.\nA third limitation is scope on coordination between multiple agent workers. Our claim\nthat most harness interventions add little on top of a plain coding agent (Section [4](#S4))\nis made almost entirely with a single worker; we do run one coordination ablation\n(Section [4.4](#S4.SS4)) across a small set of coordination primitives on top of\nmultiple parallel workers, but we do not otherwise invest in coordination research\nbetween multiple concurrent streams of work. We defer this to future work, since it is\nits own interesting problem, plausibly with a different set of useful interventions than\nthe single-worker setting, and one that likely requires an even larger compute budget\nthan what we use here to study properly.\nA fourth limitation is possible asymmetry in tuning effort: because Malena is our own\nsystem, it is natural to worry that we invested disproportionately more debugging and\nconfiguration effort into it than into the external harnesses it is compared against,\ninflating its apparent advantage. We mitigate this by treating every harness’s backbone\nport the same way we treat our own: each external harness went through its own\nbackbone-specific verification pass before its canonical batch was launched, which\nsurfaced and required fixing genuine incompatibility bugs in the harnesses’ own code\n(e.g., independent tool-calling failures in both MLEvolve and ScienceFlow specific to\nGLM 5.2), and beyond bug-fixing we additionally ran targeted configuration ablations on\nScienceFlow and Arbor (worker count, resource-admission\npolicy, executor timeout, and early-stopping aggressiveness) to check whether their\ncanonical settings were leaving performance on the table.\nAppendix [D.3](#A4.SS3) reports this work in full; none of these\nablations moved outcomes by more than run-to-run noise at our sample sizes, so we kept\neach harness’s original canonical configuration, but we surface the negative results\nhere rather than reporting only the positive tuning story we have for our own system.\nG.2 Broader Outlook\nBeyond the direct ablation results, our observations across backbones and prior harnesses point at two related hypotheses about why scaffolding is losing its edge, which we lay out here as motivation for future work rather than claims this paper establishes.\nPost-training ate the harness. Frontier LLMs are increasingly post-trained directly inside a coding-agent loop – rewarded for planning, executing, and debugging across many turns of real tool use – rather than only on single-turn completions. We hypothesize that this kind of post-training substitutes for exactly the scaffolding that a plain coding-agent environment (Oneshot) would otherwise need on top of a chat completion (Chat): search over what to try next, recovery from a failed step, deciding when a result is good enough to stop on. If so, the Chat-vs-Oneshot gap (Section [4.1](#S4.SS1)) should track how much of this coding-agent post-training a model has received, more than it tracks raw model scale. We see suggestive evidence for this in the DeepSeek V4 family: the Preview releases show close to no gap between Chat and Oneshot performance, while the final releases – built on comparable base models but with substantially more coding-agent post-training – open up a clear gap, though still narrower than the gap we measure for GLM 5.2 (Section [4.1](#S4.SS1)). If this pattern holds more broadly, it reframes a common motivation behind self-evolving-harness designs, where an agent is given the ability to rewrite its own scaffolding to better match its abilities ([Wang et al., 2026a](#bib.bib42)): rather than each model needing a harness custom-fit to it at inference time, post-training may already be doing this fitting once, in advance, for every downstream task the model is later pointed at.\nCoding agents as the bitter lesson for test-time inference. A second, related reading of our results is architectural rather than about training data: for models capable enough at autonomous tool use, adding hand-designed structure on top of a plain coding-agent session – explicit search trees, planner/executor splits, multi-worker coordination – has a poor and often negative return (Section [4.2](#S4.SS2)–[4.4](#S4.SS4)), while simply running more (and more capable) coding-agent post-training inside that same plain loop could potentially perform better. This is the same shape of argument Sutton makes about general-purpose search and learning methods outscaling hand-engineered domain structure as compute grows ([Sutton, 2019](#bib.bib40)), applied to test-time inference specifically: a basic coding-agent harness plus a stronger backbone tends to close the gap that a specialized harness had opened at a weaker backbone, rather than the specialized harness’s advantage compounding. We see the same qualitative pattern in our own results: weaker backbones still benefit measurably from hand-designed workflow priors like MLEvolve’s tree search, but as backbone agentic capability increases, Malena’s plain single-session harness closes that gap and matches or exceeds MLEvolve without any of its search machinery (Table [15](#A4.T15), Appendix [D.2](#A4.SS2)). Taken together with the first hypothesis, the practical implication is the same one drawn in Section [6](#S6): the harness is not where the durable advantage lives.", "segments": null}]}
